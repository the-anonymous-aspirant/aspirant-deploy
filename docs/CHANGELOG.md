# Changelog

### 2026-08-29
- Make `scripts/auto-pull.sh`'s freshness gate fast-forward the deploy checkout instead of only reporting it stale (system_3 #4537). Gate 3 shipped report-only under #2534 with "escalate to a refusal?" left as an open operator decision; the outcome was neither — `checkout_stale` fired on essentially every five-minute tick from 2026-07-20 to 2026-08-29, forty days, `behind:11` by the end, and nothing pulled, so every `aspirant-deploy` merge in that window landed in a repo the cell was not running from (the #4507 enumeration fix among them). The gate now runs `git merge --ff-only origin/main` when git can prove it lossless — no tracked file modified or staged, `HEAD` an ancestor of `origin/main` — logging `checkout_ff` with the old and new commit; otherwise it logs `checkout_stale` **with the reason** (`refused:tracked_changes`, `refused:not_fast_forward`, `failed:merge`), which are exactly the cases a person has to resolve. `--dry-run` logs `would_checkout_ff` and touches nothing; a maintenance pause still freezes the checkout because gate 1 exits first. A refusal was the wrong escalation (a compose-file lag would wedge every image deploy); a fast-forward is not an escalation, it is the command the warning was asking a human to run. Git replaces files by inode, so the running copy of the script is unaffected mid-tick (verified). Unit coverage in `tests/auto_pull_unit.sh` gains the preflight/refusal cases and a cron-shape run of the whole script inside a scratch clone (dry-run, live fast-forward, refused). That cron-shape run found a second, older defect, fixed here: the flock re-exec (`exec … flock -n "$LOCK_FILE" "$0" "$@"`) ran after the flag loop had `shift`ed `"$@"` empty, so on the locked path — every cron tick and every hand invocation without `ASPIRANT_AUTO_PULL_LOCKED` set — `--dry-run` deployed for real and `--service NAME` swept every service. The original argv is now captured before parsing and passed through.

### 2026-08-28
- Enumerate `scripts/auto-pull.sh`'s sweep by the ref each container was created from, not by the ref `docker compose ps` prints (system_3 #4507, instance in #4489). `list_aspirant_services` filtered on the ps `{{.Image}}` column, which resolves through the local tag store: it reads `…:latest` only while that tag still points at the running image and a bare `sha256:…` once it has moved on. Two things move it — a hand `docker pull` (#4184, 2026-08-23) and the script's own failed blue/green (2026-08-26: `docker compose pull` re-pointed `:latest` at the candidate, `deploy-client.sh` rejected it on health, the rollback left the tag on the rejected image) — and either dropped the service from every later tick with no decision line saying so, which is how 20 operator-merged aspirant-client PRs sat undeployed for two days until a health red was read by hand. The filter now keys on `docker inspect {{.Config.Image}}`, the compose file's `image:` string, which does not move; a service in that state now logs `deferred_known_bad` every tick until a good build lands, and deploys it when one does. The pure half is `is_polled_image_ref` + `select_polled_services`, sourced under `ASPIRANT_AUTO_PULL_LIB=1`; `tests/auto_pull_unit.sh` gains seven assertions including the bare-image-ID regression. The one-off recovery for the current instance was the operator-authorized `docker tag <running-id> …aspirant-client:latest` (#4489 c24884); this makes that hand step unnecessary next time.

### 2026-07-20
- Issue the explorer's read-only credentials from the bootstrap, and prove they are read-only by being denied (system_3 #2542, bridge in #2540). `scripts/lake-skeleton.sh` now creates `lake-skeleton-explorer-ro` with `bucket allow --read` and no `--write`, plus a SELECT-only `explorer_ro` catalog role, writing both into the credentials env-file under the names `docker-compose.yml`'s `explorer-api` already reads. Both credentials previously existed **only as hand-made artifacts on the cell** — correct on that host, absent from this repo, and the dev box is the control group: it ran the same script and its Garage holds exactly one key, `lake-skeleton-rw`. Since `LAKE_SKELETON.md` makes destroy-and-recreate an acceptance criterion, the operator's "bounded by a read-only key" held today and would have stopped holding silently after the next rebuild, with `EXPLORER_S3_ACCESS_KEY` accepting whatever it was handed. The bound is now reproducible, and the binding is real rather than assumed: before this change the cell's env-file carried no `EXPLORER_S3_*` at all, so the compose default resolved empty and the service was wired to no key rather than to the read-only one. `verify` gains four checks that attempt the write and require it to fail — a denied `PUT` and a denied `CREATE TABLE` are evidence; the acceptance criterion, the compose comment, and the explorer's own source all merely asserted it. Re-grants `--read` on every run because creation and permission are separate operations in Garage, so an existing key proves nothing about what it may do. `env_set` replaces the bare `sed -i` substitution, which silently did nothing when a key was absent — the case for every env-file created before this change, which would have reported success while leaving the explorer uncredentialed.
- Report `aspirant-deploy` checkout drift before `scripts/auto-pull.sh` deploys from it (system_3 #2534, root cause in #2520). A third gate runs after the provenance check: `git fetch origin` (read-only) then `HEAD..origin/main`, appending one `checkout_stale` decision with the behind-count and warning on stderr. It **reports and continues** rather than refusing — whether staleness should escalate to a refusal as gate 2 does is an open operator decision — and is silent when current, so the ledger does not gain a line per tick. Gate 2 proves the checkout is release-*tracking*; it never proved it release-*current*, and `docs/OPERATIONS.md` states that gate's own intent as "prove provenance, not merely fail to disprove it". A checkout six PRs behind on `main` passed it cleanly, which is how the cell sat at PR #50 while origin/main was at #56: nothing on that host has ever pulled the checkout, because auto-pull.sh polls images and carries no git operation and no other cron does either. Since the deployed compose file comes from that checkout, image updates were still being recreated every five minutes from six-PR-old config, silently — stale docs were never the risk. The fetch is best-effort: an unreachable origin logs `checkout_freshness_unknown` instead of blocking, because turning this host'"'"'s flaky uplink into a deploy outage would be worse than the defect being reported. Unit coverage extended to 33 assertions in `tests/auto_pull_unit.sh`, including one asserting a stale checkout still passes the provenance gate — the gap this closes.
- Version the Cloudflare DDNS updater as `scripts/update-dns.sh`, reading its credential from an `aspirant`-owned `0600` env file instead of carrying it inline (system_3 #2393). The unversioned `~/update-dns.sh` on the cell hardcodes a live zone-wide Cloudflare token at line 5 of a mode-775 file in the home directory, unchanged since March; anything able to read it can repoint the apex A record, which is the whole domain rather than the two records the job maintains. The replacement fails closed — a missing, unreadable, or blank-valued env file exits 1 before any request goes out, rather than falling back to an empty token in a 5-minute loop. Also fixes a real bug carried by the original: the `home.the-aspirant.com` response was captured and never checked, so a failed update of the SSH entry point logged as a success while web traffic followed the new IP — both responses are now checked and logged distinctly, and either failure exits non-zero. `scripts/ddns.env.template` documents the four values; `tests/update_dns_unit.sh` covers the pure logic (18 assertions, no network); `docs/OPERATIONS.md` §Cloudflare DDNS credential carries the install, rotation, and verification runbook. Repo-side only — the cell is untouched and the exposed token is still live. Rotation is dashboard-only (an API token cannot mint or revoke tokens) and it plus the cutover land together in an operator-picked window.

### 2026-07-19
- Gate `scripts/auto-pull.sh` on a maintenance marker and on compose-file provenance (system_3 #2279-B1). Two checks now run once per tick before any pull or recreate. (1) A `.maintenance-pause` marker in the checkout root makes the tick a logged no-op exiting 0, letting an operator freeze deploys mid-cutover without editing the crontab; the filename and presence-is-the-signal contract match system_3's `shared/paths.py`, but the marker is per-host because the two boxes share no filesystem. (2) The run refuses to act, exiting 1, unless `HEAD` is `main` tracking `origin/main` — the script deploys from the compose file in its own checkout, so a checkout parked on a feature branch would recreate production services from an unreviewed `docker-compose.yml`; a detached HEAD or absent upstream is a refusal, not a pass. Neither gate looks at working-tree cleanliness, so the cell's stray `.bak` files do not wedge deploys. Rollback and known-bad-SHA caching are untouched. Preventive — the cell was measured clean. Unit coverage in `tests/auto_pull_unit.sh` (27 assertions).
