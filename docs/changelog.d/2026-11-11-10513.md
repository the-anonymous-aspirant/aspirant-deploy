- `lake-skeleton.sh seed` now refuses to run if the catalog's `asset_inventory` or `ingest_runs` already holds a row whose `dataset_id` isn't the fixtures' own (system_3 #10513).
  - **Why.** `scripts/lake_skeleton_fixtures.py`'s `replace()` helper unconditionally drops and recreates every silver/gold table it writes, discarding whatever was there first — fine while the catalog only ever held fixtures, and not fine the day real data first shared it with them. A 2026-11-02 reseed (run on the stated premise that `seed` is "safe to re-run anywhere") silently destroyed six real financial records' catalog rows, and their wrapped DEKs, three days after they were loaded and independently verified. `asset_inventory`/`ingest_runs` are the only two tables `catalog.py`'s schema gives a `dataset_id` column, so they are the only ones a row-level check can cover; the guard refuses the whole run (every table `replace()` would touch, not only these two) if either shows foreign data, on the reasoning that a catalog in genuine use is not safe to reseed at all.
  - **What it does.** `_refuse_if_real_data_present()` runs right after `USE lake`, before `replace()` is even defined: for each of the two tables, if it exists and holds any row with `dataset_id != SYNTHETIC_DATASET_ID`, the script exits non-zero with a message naming the table and count, rather than proceeding. Also corrects the "safe to re-run anywhere" comment in `lake-skeleton.sh` that licensed the original incident, and notes the same caution on `ingest`.
  - **Verified** against the real `lake-skeleton-catalog`, read-only: the exact guard query (same DuckLake/postgres connection shape `fixtures.py` uses) correctly reports foreign rows in both tables in the catalog's current (post-incident) state — `lake_catalog_unit.sh`'s 21 contract checks plus its 6 cross-file checks (unaffected by this change) still pass. No isolated automated test exists for `fixtures.py`'s live-catalog behavior (none existed before this change either); building one needs a disposable postgres+S3 harness distinct from the shared skeleton, noted as a gap rather than solved here.
  - **Not in scope:** the longer-term fix security and I agreed on — fixtures seeding their own catalog and bucket, never the one holding real data — is a bigger architectural change, filed separately in spirit on #10513 rather than built in this PR.
