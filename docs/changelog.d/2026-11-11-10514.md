- A second, separate `docker-socket-proxy` sidecar, `docker-socket-proxy-write`, carrying the one write capability the admin start/stop control needs (system_3 #10491-A / #10514).
  - **Why.** The existing sidecar (`CONTAINERS: 1, SYSTEM: 1, POST: 0`) is read-only by design, and `CONTAINERS=1` is a blanket `^/containers` path match with no method restriction of its own (confirmed against the real `haproxy.cfg` this image ships, not assumed) — flipping `POST: 1` on that same sidecar would, through that one rule, also grant create/remove/rename/kill/exec-create on any container, not just start/stop. A second, narrower sidecar is the only way to add start/stop without widening the existing one.
  - **What it does.** `docker-socket-proxy-write` carries `POST: 1, ALLOW_START: 1, ALLOW_STOP: 1` and nothing else — no `CONTAINERS`, so it cannot list or inspect, only start/stop a container whose id/name it is given. `monitor` gets a second env var, `DOCKER_SOCKET_WRITE`, pointed at it; every existing read in that service keeps using the original `DOCKER_SOCKET` sidecar, unchanged. Mirrored in both `docker-compose.yml` and `docker-compose.dev.yml`.
  - **Not a container-name allowlist.** This proxy would permit start/stop on *any* container id if asked, including this cell's own infrastructure — that scoping lives in aspirant-monitor's own code (system_3 #10514), not here.
  - **Tests.** New `tests/compose_docker_write_proxy_scope_unit.sh`: the new sidecar never carries a truthy `CONTAINERS`, does carry `POST`/`ALLOW_START`/`ALLOW_STOP`, and no service but `monitor` shares its network or references `DOCKER_SOCKET_WRITE` — checked against 4 negative-control fixtures, 1 positive control, and both real committed compose files.
