- Add a streaming AOBJ writer, `encrypt_object_stream`, to `scripts/kek/dek_envelope.py` (system_3 #9757, #9546-A1).
  - **Why.** `encrypt_object` builds the whole encrypted object in memory. Wrapping a 5 GB `sensitivity=high` upload, the explorer upload epic's ceiling (#4121), would need about 10 GB resident. The cell has 15 GB in total and about 7 GB free under load.
  - **What it writes.** The new writer reads and encrypts one 8 MiB chunk at a time with an incremental AES-256-GCM encryptor. It uses the same 5-byte header as AAD and emits the same `header ‖ nonce ‖ ciphertext ‖ tag`. The output is therefore byte-identical to `encrypt_object` for the same key and nonce, and `decrypt_object` and the explorer's read path open it unchanged. The format version does not change.
  - **Nonce.** The nonce is always drawn fresh from `os.urandom`; no caller can pass one. The promotion runner can verify a claimed digest in the same pass through an optional `plaintext_hash`.
  - **Truncation.** A source that returns `None` (a non-blocking stream with no data yet) is refused with `EnvelopeError`, not read as end of file, which would finish a valid object over a prefix (security review). The docstring tells callers to check the returned length or `plaintext_hash` before committing the output.
  - **Tests.** `tests/kek_envelope_stream_unit.sh` runs 32 checks in `python:3.11-slim` with `cryptography==46.0.3`, the version the runtime images pin:
    - streamed and one-shot bytes match at 0 and 1 bytes, one under, at and one over a chunk, several chunks, and 3 MiB, and every result decrypts;
    - bad keys, nonces and chunk sizes are refused, and so is a `None` read mid-stream;
    - a tampered streamed object fails the tag;
    - 512 MiB streams with peak RSS up 16.7 MiB, against 1538 MiB when the same input is pushed through as one chunk.

    The module's `--self-test`, which is also the recovery drill, is unchanged.
