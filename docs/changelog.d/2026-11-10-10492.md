- Staged the real lake KEK to a tmpfs file for every `lake-skeleton.sh` verb that can reach `compose`, not only `ingest` (system_3 #10492, security post-merge review of #10354).
  - `promote` and `verify-at-rest` still passed a real `LAKE_KEK_HEX` straight through `compose`'s env interpolation, which dockerd persists under `/var/lib/docker` on this cell's unencrypted root LV — the exact leak #10354 closed for `ingest` alone. `gmail_pull_and_ingest.sh --verify` exports the KEK once for both its `ingest` and `verify-at-rest` children, so the same gap reached the one real-key path #8814's Gmail pull is documented to use.

  - `stage_real_kek` and `gmail.sh`'s own KEK staging now refuse a non-tmpfs `$XDG_RUNTIME_DIR`, so a misconfigured caller cannot put the key on disk.
  - New `tests/lake_skeleton_kek_guard_unit.sh` and `tests/gmail_pull_and_ingest_kek_guard_unit.sh`, each with a negative control proving the leak is caught when the guard is removed.
