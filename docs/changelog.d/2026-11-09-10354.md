- Stop handing the lake KEK to a container by `-e` (system_3 #10354, security review #8813).
  - **Why.** dockerd persists a container's `-e` values under `/var/lib/docker/containers/<id>/` on this cell's unencrypted root LV for as long as the container exists, and `docker inspect` shows them to every member of the `docker` group. Every place that gave a container the lake KEK (`scripts/gmail/gmail.sh`, `lake-skeleton.sh ingest`) used `-e LAKE_KEK_HEX`, violating `KEK_CEREMONY.md`'s own "never at rest on the cell's disks" for any run that used it. No real KEK had gone through this path yet; this fixes it before #8814 (the first real pull) runs.
  - **What it does.** `scripts/kek/kek_loader.py` (and its copy in aspirant-explorer) gains `load_kek_from_file` / `LAKE_KEK_FILE`, preferred over the env var in `require_kek`, and refuses a group- or world-readable file. `gmail.sh` and `lake-skeleton.sh`'s `ingest` verb now write the hex to a 0600 file under `$XDG_RUNTIME_DIR` (tmpfs), bind-mount it read-only, pass `LAKE_KEK_FILE` instead of `-e LAKE_KEK_HEX`, and delete the file on every exit path (success, failure, or `set -e`). `scripts/lake_ingest.py`'s own `main()` had an independent direct call to `load_kek_from_env` that bypassed `require_kek` entirely — found while proving this live, not from the task body — and now tries the file first too.
  - **Unaffected on purpose.** `seed` (the synthetic fixtures loader) and `scripts/lake_skeleton_fixtures.py` keep the plain env var — the task that drove this fix explicitly keeps `LAKE_KEK_HEX` as the tests-and-synthetic-skeleton-only path.
  - **Residual, out of scope, noted in `KEK_CEREMONY.md` §8 per the task's own call:** swap. `/swap.img` is on the same unencrypted root as `/var/lib/docker`.
  - **Also residual:** `promote` (task #9758 / aspirant-deploy PR #122, not yet merged) needs the identical `stage_real_kek` treatment once it lands — flagged on that PR. `lake_verify_at_rest.py`'s own direct `load_kek_from_env` call is the same shape of gap but was not in this task's scope; noted for a follow-up.
  - **Tests.** `scripts/kek/kek_loader.py --self-test` (both repos): a 0600 file loads, a 0644 file is refused, the file wins over a conflicting env var — 16/16. New `tests/gmail_sh_unit.sh`: no `-e LAKE_KEK_HEX` ever reaches `docker run` argv, `LAKE_KEK_FILE` is passed instead, the file is 0600 while held and gone after both a successful and a failing run — 11/11, confirmed as a genuine negative control (reverting the fix makes it fail). `tests/lake_skeleton_unit.sh` gained `stage_real_kek` coverage (unsets `LAKE_KEK_HEX` after staging, so `compose`'s own interpolation never sees it) — 58/58, same negative-control check. `tests/lake_ingest_roundtrip.py` gained a `main()`-level KEK-resolution test (file alone, env alone, file-over-env precedence, and the fail-closed refusal with neither) — 74/74, same negative-control check. No regressions in `envelope_ingest_unit.sh` (16), `lake_verify_at_rest_unit.sh`, `gmail_pull_and_ingest_unit.sh` (12), or the explorer's own pytest suite (33 passed, 46 skipped — no live DB/S3 in this run).

Ran `lake-skeleton.sh ingest --dry-run` for real against the live skeleton with a high-sensitivity record and a synthetic KEK: `written high 1`, proving the file is genuinely read inside the container, not just passed; reverting the `lake_ingest.py` fix and re-running the identical live command genuinely fails to find the KEK, confirming the fix (not a coincidence) made it work.
